# Camera capture

JPEG is the default for video-frame capture, using an opaque sRGB canvas at quality 95. A device's full-resolution still capture is retained for upload. The Docker worker reads the primary image of JPEGs containing MPF/MPO auxiliary data, so a still with an embedded gain map does not trigger the animation/multi-page error. No phone format setting or browser-side recompression is needed. [Pillow's MPO documentation](https://pillow.readthedocs.io/en/stable/handbook/image-file-formats.html#mpo) describes primary-image selection.

**Take photo** opens PakTrak's camera. Allow camera access, frame separated cards with every edge visible, and use the large bottom capture button. The guides are optional and are never drawn into the photo. The preview displays the whole camera frame without cropping or stretching it. Portrait and landscape layouts, safe-area spacing and the selected appearance apply to the controls.

Use **Camera**, above the capture controls, to choose a camera after granting permission. The list uses the camera names supplied by the browser (for example, wide, ultra-wide, telephoto or front cameras); unnamed entries receive numbered labels. **Automatic · rear camera** restores the default rear-camera preference and shows the camera actually opened. Compare the live preview to find the clearest card text. PakTrak remembers a working selection in this browser on this device, independently of account settings. Clearing site data removes that preference. If a remembered or selected camera is missing or busy, PakTrak returns to Automatic with a visible notice. If listing devices fails, the current camera remains usable.

The [device list](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/enumerateDevices) contains only cameras the browser makes available with the granted permissions. It may not expose every physical lens separately; **Phone camera** remains available for the device's own camera controls. PakTrak requests a chosen camera by its exact device identifier using [`getUserMedia`](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia), stopping the previous stream before opening the next. Light and zoom controls update for the newly opened camera. Switching is disabled while opening a camera or taking a photo; photo review keeps the captured image until **Retake**, upload or confirmed dismissal. No lens choice changes the upload format or creates a scan by itself.

**Check your photo** shows its actual pixel dimensions and the foil count from the upload form. Enlarge it to inspect text and reflections, retake it, or choose **Upload & scan**. Capturing or retaking does not create a scan or consume the guest allowance. A failed upload keeps the same captured File and upload receipt in the open review so retry does not need another photograph. The photo is held in this page's memory until uploaded; it is not added to the phone's photo library or persisted for recovery after closing/reloading the page. Closing a captured photo asks before discarding it. Once server acceptance is confirmed, the batch opens and processing can continue with the phone disconnected.

**Phone camera** retains the native camera/file-input route for full-resolution photos, HEIC/HEIF and device-specific controls. **Library** selects an existing photo. File-input capture is a browser/OS hint, so some devices show a picker. These routes remain available if browser permission is denied, a camera is busy or missing, or the in-app camera API is unavailable. Live camera access needs HTTPS (or a browser-trusted local development origin). See the [WebKit capture guidance](https://webkit.org/blog/7763/a-closer-look-into-webrtc/) and [HTML capture documentation](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Attributes/capture).

By default, the in-app camera requests the rear-facing device, high-resolution video preferences and no audio. Resolution preferences do not promise a phone's full sensor output. When implemented by the browser/device, `ImageCapture.takePhoto()` requests a still photograph at the largest reported dimensions that fit the pixel budget. Otherwise, a canvas encodes the **actual video-frame dimensions** as JPEG at quality 95. It does not enlarge the frame or include UI overlays. Review explicitly labels the video-frame fallback and points to Phone camera for more detail. Photo capabilities, optional light/zoom controls and applied settings are detected at runtime, as described by the [W3C Image Capture specification](https://www.w3.org/TR/image-capture/). Unsupported/rejected controls do not pretend to change the camera.

Tracks stop after capture, when closing, when switching to the native camera/library, when the page becomes hidden or when the component unmounts. An interrupted/backgrounded live view requires **Resume camera**. If a delayed permission grant arrives after closing, the returned tracks are stopped. Captures that finish after cancellation are discarded. Blob preview URLs and temporary canvas buffers are released. CSP permits local blob images/media for the preview without adding a remote photo service or inline scripts.

The browser performs capture and optional preview only. Docker still owns normalization, region detection, OCR, matching, confidence decisions and collection updates after durable acceptance. This UI does not measure blur, detect glare, promise a particular card count or claim live card recognition. Still capture resolution and optional controls vary by browser and hardware; physical iPhone/Android testing is still required. Large layouts may need the native camera route or smaller groups of cards. See [photo formats](PHOTO_FORMATS.md) and [scan batches](SCANNING.md).

Browser tests use real canvas-backed MediaStreams with synthetic card-shaped tiles, while stubbing device permissions, reported capabilities and the optional still-photo API. They exercise whole-frame pixel preservation, dimensions, review/retake, upload retries and acceptance, stopping tracks, late permissions, background interruptions, unsupported controls, camera selection/persistence, missing or busy cameras, device-list changes, blocked storage, cancellation during lens switching, fallback selection and mobile layouts. This is browser-engine/lifecycle evidence, not physical-camera autofocus, lens or image-quality qualification.
